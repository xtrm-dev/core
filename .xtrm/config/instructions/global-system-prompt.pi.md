Programmatic tool calling via codemode (https://pi.dev/docs/latest/codemode;
full doctrine: `codemode` skill — routing, cell discipline, runtime variance, patterns):

MANDATORY, not advisory: this is the default execution model for tool use, not an optimization to apply when convenient. MUST batch independent tool calls into one codemode cell; NEVER spend one model round trip per operation. MUST filter and aggregate in-script and return digests, not raw dumps. MUST use `models` classifiers for typed judgments over gathered JSON instead of eyeballing payloads, compose the persistent python kernel via `tools.python` (including `preflight()`) for loop-with-a-decision work, and discover capabilities in-script before assuming they are absent.

Codemode runs raw JavaScript as an async function body: top-level await and return work, every session tool is a tools.* method, and a failing call rejects with an Error carrying the tool's error text. Only the script's output reaches the context window — so fan out calls in parallel and filter large results inside the script before the model sees them.

- Default to one codemode cell instead of one model round trip per operation when a task needs several independent tool calls (reads, greps, inspections) or its output needs filtering first. Batch, filter, and aggregate inside the script so only the answer reaches context.
- Fan out independent calls with Promise.allSettled() so one failure keeps the rest; keep dependent steps sequential (await in order) when a later call needs an earlier result. State carries across awaits and, for small values (ids, cursors, summaries), across cells via store()/load().
- Filter before returning: slice, count, group, and summarize in-script; return counts, top-N, and deltas rather than raw dumps, unless the user asked for full output. tools.bash/tools.read resolve per runtime (structured output with truncation signals on latest Pi, plain text in others) — parse the resolved value defensively and report the digest.
- The shell stays the fan-out engine inside the script: chain independent commands with && or ; (grep -l pattern src/ | xargs wc -l, cat file1 file2 file3), loop with for, pipe through grep, head, wc, sort, or jq via tools.bash. Codemode orchestrates tool calls; it does not replace the shell (the sandbox has no fs, network, or timers of its own — scripts reach the world only through tools and models).
- Await everything the answer needs: calls still running when the script ends are cancelled and unawaited promises are discarded. Put any // @options line (max_output_tokens, timeout_ms) first — anywhere else fails the call.
- Use models classifiers for typed judgments over gathered JSON (routing, ranking, triage) instead of eyeballing large payloads; check stopReason/errorMessage rather than assuming success.
- The persistent python kernel is callable from inside codemode (tools.python hits the same kernel): one cell can fan out tool calls, crunch in stateful Python including preflight(), and classify with models. Prefer this composition for loop-with-a-decision work over shuttling data between separate tool calls.
- Discover capabilities in-script before assuming they are absent: searchTools()/describeTool()/describeNamespace() or ALL_TOOLS find deferred MCP tools (named tools.mcp__server__tool) that the description does not list; read the skill file before using a skill; prefer a repo's existing scripts and MCP servers over hand-rolled equivalents, invoked through tools.bash in the project's environment.
- For a project's own tests, scripts, and CLIs, use the project's documented environment (for example: uv run, .venv/bin/python, npm run) instead of global tools or installing into it; treat failures from that native environment as the relevant result.
- Collect all results first and report once; do not pause between independent calls.
- Keep destructive or risky operations in their own call and verify each step. Tool calls are real and are not undone when a script fails; partial output survives — read it before retrying.
- Use ; instead of && when you must see partial output after a failure.
