XTRM · Substrate design note · 2026-11-11

Linking a Substrate issue to its pull request

A pull request can be the work that delivered an issue, or a page that merely mentions it. Today Substrate stores neither. This design stores both, labels which is which, and shows the link in the CLI and in the console without guessing.

T2 reads the PR’s own commits, so squash does not erase it. Verified on core PRs #893 (5 commits), #865 and #863 (1 each): every commit returned by pulls/N/commits carries XTRM-Issue: after a squash merge. The squash setting decides what reaches main, not what the PR can prove. The real blocker is the step 6b hook, which is not installed: 3 of the last 100 squash commits on core’s main carry the trailer, 0 of 100 on xtrm. A direct PR to main gets T2 as soon as the hook lands; a coordinator chain needs COMMIT_MESSAGES so the writer’s trailers survive the second squash. pulls/N/commits is capped at 250 commits. Above that, sb links check records “T2 unverifiable: PR exceeds 250 commits” and the issue falls back to T1 or an operator decision; no second retrieval path. (If one is ever added, it must page and compare base.sha…head.sha, never branch names.)
The 30-second version

One PR, two very different claims

A worker opens xtrm-dev/xtrm#335. The title says XTRM-718. The opener records the PR against XTRM-718 in the same step — today the gh shim, later the host (step 27). The issue page and sb issue show now display a chip. Closing XTRM-718 may cite #335.

Later, someone writes “the same fix as #339” in a comment. The reconciler sees #339 and records it too — but as mentioned. XTRM-718 will never close on #339, because #339 did not carry this issue’s work; it was only named in prose.

The rule in one line: the field shows both links, with a label. Only created_from is delivery evidence; mentioned is a pointer.
Semantics

Why a single “PR field” would be wrong

GitHub numbers PRs per repository, so a link always needs owner/repo plus the number. And the two claims above have different evidence, different writers and different consequences at close. Collapsing them produces predictable failures: a title-only PR closing an issue it never touched, a cross-repository #335 resolving to the wrong project, or a prose mention being counted as delivery.

GitHub and Jira users already know the difference: “Closes #123” versus “mentioned in #123”. This design keeps that distinction and stores it instead of inferring it at read time.

The model

Three identities, four stores

The issue is the authority. Jira is the human-facing view; GitHub is where the code and the PR live. Each arrow is a stored row with a writer, a source and a time — never a sentence in a close reason. State is a separate row: the link says “this PR is this issue’s work (or mentions it)”, the pull_requests row says what the PR is doing now.

How a link is made

Strong evidence at open, weak evidence at repair

Automatic by default. You do not type a link. When the host opens a PR it writes created_from; when a PR’s title, body or branch names an issue, the reconciler writes mentioned. Both land in the same field, in the CLI and on the issue page.

Why xt end is not the writer

It is old, it is broken for this repository’s commit style, and almost nothing uses it. Verified on 2026-11-11:

  • xt end --dry-run in this worktree produced title “Xtrm-app”, one issue xtrm-app, and Closes: xtrm-app. It read the conventional-commit scope (xtrm-app) as an issue ref (end.ts:191), then invented an issue when both sb and bd failed to resolve it.
  • Its body markers appear in 0 of the 80 most recent core PRs and 3 of 80 XTRM PRs; the newest is 2026-10-14.
  • It force-pushes, rebases and removes the worktree — three destructive steps an agent session should not own.

Keep it out of the link path. If it is kept at all, fix extractIssueIds separately; the reconciler (step 26) is the backstop for every PR the opener misses.

The host path is the strong one: the host knows the issue and the PR it just opened, so it writes the evidence and the link in one transaction. The reconciler path exists for PRs the host did not open, and it may only record what the evidence supports. Typing #335 in an issue comment does not create a link by itself; links are written from PR-side evidence or by the explicit mention verb.

Five rules the writers share

  1. One writer per relation. Step 14 owns created_from; the mention verb and the reconciler own mentioned. No second path writes the same relation.
  2. T1 needs a receipt; T2 needs the XTRM-Issue trailer. artifact_bindings.receipt_id stays NOT NULL. T1 without a receipt is refused with the next action; T2 is a commit trailer that names this issue. Neither falls back to a journal note. Live receipt means: not superseded, and its execution binding is the issue’s current revision; claim liveness is checked separately in b1/b2.
  3. Canonical value. Accept github:org/repo#n, org/repo#n, a github.com PR URL, or a bare #N scoped to the issue’s repository; store org/repo#n. A bare number is never resolved against “whatever repository is selected”.
  4. Cross-issue guard. A trailer receipt must belong to the issue being linked. A foreign receipt produces mentioned plus a check finding, never a silent attach.
  5. One transaction. T1 created_from ⇒ artifact + link row + provenance event, together. T2 created_from ⇒ link row with commit SHAs. mentioned ⇒ link row only. A provenance row without its artifact is an orphan; sb links check reports it.

Enforcement

The gate joins two rows; it does not read prose

Build order step 15 requires a live claim, a result entry, and a PR or commit record before close. This design makes “PR record” precise: a created_from row plus its live artifact on the receipt. A mention, however visible, is refused with a reason the operator can read.

Two gates, one conjunction

Manual close (step 15) accepts a live claim, a result entry, and T1 or T2 even while the PR is open; the stage stays merged-pending and the reconciler completes it later. This keeps the close path free of live GitHub reads.

Auto-close (step 27) requires the full conjunction: T1 or T2, merged into the default branch, no other open PR linked to the issue, no live claim still working, no deploy or production window in the contract. The PR clause is one conjunct, never the whole gate.

Until step 26 stores merge state, “merged to default” is a live gh read. An unreachable GitHub is fail-closed: the operator override is a reason string that writes a Journal decision, exactly like the merge guard. Unknown never passes.

T2 names its evidence in a child table: issue_pr_commits(issue_id, repository, number, sha, landed_sha, trailer_revision), indexed on sha so provenance commit and the step-27 revert check read SHA→issue in one hop. New pushes append rows. landed_sha is the one host-owned finalization, set when the merge lands. trailer_revision is audit only; a mismatch is reported, never gated. A conflicting writer keeps the first row and records links check “commit claimed by two issues”; it never throws, so one bad commit cannot stall the poll. T2 reads every XTRM-Issue: value on a commit: more than one distinct issue yields no T2 row plus a finding, because parseTrailers (packages/substrate/src/domain/provenance.ts:108) is last-wins today and must gain an all-values form before T2 ships. landed_sha is deliberately not unique: a squash commit on main can carry trailers for several issues, and the step-27 revert check resolves landed_sha through the child rows instead of re-parsing the main-branch message. A later sb links check finding flags T2 commits with no Agent:/hook marker; it does not block.

Converged rulings · 11-11. A trailer receipt must exist, must not be superseded, and must belong to the issue; otherwise the result is mentioned plus a links check finding, with no fallback to findByCommit. The gate requires the artifact on the receipt. Repeated reads tie-break with ORDER BY created_at, id. The step-14 verb runs in this order: (a) parse the input form, (b) normalize to org/repo#n, (c) resolve the receipt (explicit → live claim → latest live binding), (d) validate it exists, is not superseded and belongs to this issue, (e) attach the kind=pr artifact, (f) insert the created_from row, (g) emit the event and return the row.

Open decisions

  1. Names. created_from / mentioned matches the existing edge vocabulary (discovered_from); implements / mentions reads better in a sentence. Recommendation: created_from / mentioned.
  2. Do mentions persist? Recommendation: yes, written only by an explicit verb, with actor and time. A read-time derivation silently changes when the prose is edited.
  3. Do title/branch repairs count as delivery? Recommendation: no. They are mentions with a source, visible in links check; only receipt-bearing evidence closes.
  4. Accept the T2 trailer tier as delivery evidence? Recommendation: yes — the plan already says the Issue trailer needs no receipt (6b) and that a different PR’s trailers link the work (27). It needs one amendment line under step 26/27. No claim-only tier.
  5. Per-repo T2 capability. xtrm squashes to PR_BODY, so T2 cannot be delivery there until the setting is COMMIT_MESSAGES or a PR-body bridge exists. Recommendation: gate accepts T2 only where the merged message carries the trailer; otherwise T1.
  6. May an explicit link claim created_from without a receipt or trailer? Recommendation: no. A claim proves who is working, not what the PR contains; nothing on the GitHub side can check it.
