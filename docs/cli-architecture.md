# CLI Architecture

The `xt`/`xtrm` CLI is the control plane for XTRM's managed runtime. It launches isolated
workers, bootstraps and reconciles package-owned assets, manages the skills-v4 composition
model, coordinates Pi/Claude/Codex runtime integration, and exposes deterministic operator
surfaces such as worktree audit, merge, report, doctor, and update.

Exact flags belong to the live CLI. Use `xt --help` / `xt <command> --help` instead of
copying static flag tables into documentation.

## Entry point

`cli/src/index.ts` registers the public command families:

```text
xt / xtrm
├── pi / claude / codex       runtime launchers + isolated worktrees
├── init / bootstrap          first-time machine/runtime/project bootstrap
├── update / doctor / status  managed-state reconciliation and health
├── skills                    skills-v4 inventory, packs and active views
├── worktree / attach / end   worktree lifecycle and publication
├── merge                     Specialists-backed merge queue
├── topology                  current XTRM worker/runtime topology
├── docs / report         durable operator/reference surfaces
├── debug                     XTRM diagnostic/event tooling
├── spec                      structured planning/spec pipeline
├── release / migrate         release and one-time migration workflows
└── help / version            discovery and version/update reporting
```

The CLI should own deterministic mechanics, dependency checks, composition, and operator
UX. Higher-order judgment belongs in skills or Specialists rather than being duplicated in
large command prompts.

## `xtrm init`

`runProjectInit()` is the supported first-time bootstrap entry point. The high-level shape is:

```text
preflight
  → consolidated plan / confirmation
  → machine prerequisites
  → global managed payload
  → Claude runtime reconciliation
  → registry-owned project assets
  → Pi runtime/packages/extensions
  → skills-v4 active views
  → project bootstrap (Beads, code intelligence, instructions)
  → verification
```

`xt bootstrap` populates package-owned user-global state. `xt update --apply` is the normal
reconciliation path after initialization.

## Registry-owned assets

`.xtrm/registry.json` is generated by `scripts/gen-registry.mjs`. It describes package-owned
files under:

```text
.xtrm/hooks
.xtrm/skills/default
.xtrm/skills/optional
.xtrm/config
```

The registry also embeds `.xtrm/specialists-source.json` so a release records which
Specialists-authored skill snapshot Core vendors.

Do not hand-maintain registry hashes. After changing a managed asset, regenerate the
registry from the real repository filesystem:

```bash
npm run gen-registry
```

`check:registry-pack-parity` verifies generated/package payload agreement.

## Skills v4

The universal default surface is intentionally nine roots:

```text
using-xtrm
starting-and-resuming-work
multiplexing
planning
engineering-quality
using-specialists
gitnexus
skill-creator
find-skills
```

Domain and maintainer capabilities live in managed optional packs. User-authored packs are
flat siblings outside the package-owned `default/` and `optional/` roots:

```text
~/.xtrm/skills/<user-pack>/
<repo>/.xtrm/skills/<user-pack>/
```

Generated active views are runtime state and must not be authored directly.

Use the live command for inventory and enablement:

```bash
xt skills list --global --json
xt skills list --local --json
xt skills enable <pack> --global
xt skills enable <pack> --local
```

See `docs/skills.md` for ownership/tier semantics.

## Pi runtime

`cli/src/core/pi-runtime.ts` owns the executable managed Pi package registry. Other code and
documentation should consume that registry instead of maintaining a parallel package list.

The approved environment currently spans:

- XTRM's own `@jaggerxtrm/pi-extensions` and `pi-service-knowledge`;
- GitNexus and structural search;
- structured returns and guardrails;
- goals, tasks, background work, and subagents;
- MCP and Mermaid presentation;
- Pi↔Pi and Pi↔Claude coordination;
- worktree/process helpers and Ponytail.

The runtime supports Pi-native npm and Git package identities, including npm selectors such
as `@latest`. Managed and required are separate concepts: every baseline package is
reconciled, while the `required` bit controls health severity.

See `docs/pi-managed-packages.md` for the approved selectors and compatibility notes.

### Init/update/doctor ownership

`xt init`, `xt update`, and `xt doctor` share the same managed package model:

```text
canonical registry
   ├── init    install/reconcile
   ├── update  preview or apply drift
   └── doctor  report only
```

`xt doctor` must not mutate the machine. `xt update --apply` owns ongoing reconciliation.
The retired `xt pi install` flow is not the current package-management contract.

## Claude, Pi and Codex launchers

`xt pi`, `xt claude`, and `xt codex` create isolated execution lanes around the same XTRM
work/runtime model. Runtime adapters may inject different tools or native capabilities, but
shared durable work and skill doctrine should remain runtime-neutral where possible.

Role-shaped launchers (`--role`, `--bead`, and related live flags) compose XTRM worktree
identity with Specialists/runtime context. Consult each command's `--help` and
`docs/xt-pi-role.md` rather than freezing flags here.

## Agent instruction composition

The compact shared managed contract is authored in:

```text
.xtrm/config/instructions/agent-contract.md
```

`agents-top.md` and `claude-top.md` embed the same body between contract markers and append
only a small runtime-specific suffix. The parity test is
`cli/src/tests/agent-contract-parity.test.ts`.

Root `AGENTS.md`/`CLAUDE.md` are composite/generated consumer surfaces. Regenerate them via
the repository's normal instruction reconciliation path; do not manually splice the
canonical block into copies and let them drift.

`bd prime` is opt-in diagnostic only. Session start uses targeted Beads/Service Knowledge
lookup as defined by the canonical contract and `/using-xtrm`.

## Specialists ownership

Core vendors the Specialist-owned skills `using-specialists` and `update-specialists` from
a pinned Specialists commit. The pin and per-file source digests live in:

```text
.xtrm/specialists-source.json
docs/skills-ownership.json
docs/skills-ownership.release.json
```

Core must not locally fork Specialist-authored content. Change the source in
`xtrm-dev/specialists`, then re-vendor and update the pin.

`xt merge` remains a Core CLI wrapper backed by the canonical Specialists `xt-merge` role;
there is no separate default `xt-merge` skill in skills-v4.

## Generated and tracked outputs

Several files are deliberately generated but tracked. Their source must be changed first,
then their generator run:

| Output | Source / command |
|---|---|
| `.xtrm/registry.json` | managed asset tree → `npm run gen-registry` |
| `.xtrm/config/hooks.json` | `policies/*.json` → policy compiler |
| `cli/dist/**` | `cli/src/**` → CLI build |
| managed agent contract blocks | instruction sources → instruction reconciliation/parity path |

CI should fail on drift rather than accepting a hand-edited generated artifact.

## Worktree and publication primitives

`xt worktree` owns read-only audit/restart/branch-GC primitives and explicit cleanup actions.
`xt end` owns normal session publication/PR cleanup. `xt merge` delegates governed merge
queue behavior to Specialists.

Use live help for exact destructive/apply flags. Read-only audit should remain the default
where an operator has not explicitly requested mutation.

## Validation boundaries

Core CI verifies the architecture through deterministic gates including:

```text
package metadata
CLI build + tracked dist parity
managed-skill ownership/layout/root budgets
policy parity (Claude + Pi)
registry/package parity
Specialists vendor parity
runtime compatibility
Pi manifest/runtime safeguards
forbidden-phrase drift
tests + script tests
security workflows
```

A release candidate should additionally exercise a fresh install/runtime smoke locally,
because package resolution, Git package presence, filesystem ignore behavior, and actual
Pi/Claude runtime loading cannot be fully proven from repository text alone.
