# v0.13.0 — Substrate runtime cutover, python-kernel skillbridge, Claude channel wake

Package: `xtrm-tools@0.13.0` · Extensions: `@jaggerxtrm/pi-extensions@0.13.0`

> Pairs with `Specialists 3.21.6` (`@jaggerxtrm/specialists@3.21.6`, tag `v3.21.6`). The vendored Specialists payload is pinned to `master@5a661d16` (git-blob-sha1 digest); floating refs are rejected.

## Summary

0.13.0 moves the runtime's work authority from Beads to Substrate end to end at the infrastructure layer: project init now runs `sb init`, the in-repo `.beads/` state and its Git hooks are gone, and Substrate's MCP environment is exported on `xt claude` launches. Two substantial capability additions land alongside it — the python-kernel gains **skillbridge** (python-backed skills mounted as importable kernel modules), a **file-scoped memory preflight**, and in-kernel service-knowledge binding; and Claude sessions can now be **woken over the Specialists channel** instead of being polled. A long tail of skill-distribution, hook-scoping, and CI-hardening fixes rides along.

This is a minor bump, not a patch: it removes a work-tracking backend, changes project-init behavior, and adds new runtime surfaces. No user-facing CLI verb was removed beyond the retired `xt memory` (see Upgrade notes).

One scope caveat stated up front: this release lands the Substrate cutover for **runtime and infrastructure surfaces**. The skills/doctrine wording reconciliation is still in flight under CORE-2295, so some prose (notably `README.md`'s description of Beads as the durable substrate) still describes the pre-cutover model. Do not read this release as the completed doctrine cutover.

## Substrate runtime cutover

- **Remove committed `.beads/` state and `bd` Git hooks (PR #662 · 23d7c805).** The in-repo Beads payload and its `pre-commit` / `pre-push` / `post-merge` / `post-checkout` / `prepare-commit-msg` hooks are deleted. Boards were already migrated; this removes the stale committed state. A side effect worth noting: the persistent `pre-push.bd-sync` failure (Dolt circuit breaker, "server appears down") disappears with it, because the hook now reports no Beads database in the checkout.
- **`xt init` via `sb init --json` plus stable session identity (56dc40f2 · XTRM-252.4; f949b33f · xtrm-6qu.8).** Project/repository binding goes through Substrate's init and enrollment lifecycle; `xt init` no longer creates legacy Beads-stack state (no workspace init, no Dolt setup).
- **Substrate MCP environment on `xt claude` launches (PR #656 · e8157433; PR #659 · de62385d).** The Substrate MCP launch environment and attach additions are exported and documented, so Claude sessions resolve the Substrate MCP server the same way Pi does.
- **Gate the install-path Beads writer behind `planSubstrateMigration` (PR #660 · 6f709252).** The remaining install-path writer no longer runs unconditionally; it is gated behind the migration planner.
- **Correct `xt help` init phases (PR #663 · 7c052945).** `xt help` had still advertised the retired Beads-stack bootstrap ("install system tools (bd, dolt, bv, pi, pnpm)", "`bd init`"). Both lines now match `renderInitPlan` and `MANAGED_DEPS` — which are `sb`, `oh-pi`, `pnpm`, `gitnexus`, `deepwiki`, `ctx7`.
- **Retire the `bd-memory` stack (PR #639 · 959c7718).** The Stop gate, memory doctrine, and the `xt memory` CLI surface are removed. Memory retrieval doctrine now runs through file-scoped preflight (below) and Substrate's Journal rather than `bd prime` bulk injection.
- **Default-skill reference cutover (PR #664 · 33d03660).** Four residual normative-active Beads teachings in default skill references are rewritten to Substrate semantics (Issue revision / Journal / Closure / provenance): `engineering-quality/references/causal-debugging.md`, `reduction.md`, `multiplexing/references/messy-run-recovery.md`, and `fleet-window-dispatch.md`, where the dispatch recipe's `--bead` is now marked as the legacy alias for the bound Issue at its point of use.
- **Refresh registry asset hashes (PR #665 · b4952108).** `.xtrm/registry.json` hashes for seven assets were stale — the five skill files above plus `config/pi/install-schema.json` and `config/pi/settings.json.template`, which had drifted since 6f709252 without regeneration. Because `checkDrift` compares each registry hash to the installed file's sha256, a stale manifest produces phantom drift on every consumer machine and fails `xt update --apply --strict-registry`.

## python-kernel: skillbridge, preflight, in-kernel service knowledge

The `python-kernel` Pi extension grows from an executor into a skill host.

- **Skillbridge (309295a4 / 48cd3ae3 · xtrm-h7uwi.1).** Python-backed skills are mounted as importable kernel modules. A skill package found in a skills root becomes importable inside the kernel, so a skill's Python can be exercised directly rather than shelled out to.
- **File-scoped memory preflight (PR #611 · e6124b78; 952a1bc5).** A preflight prelude performs file-scoped memory retrieval before a file is edited, replacing the retired bulk memory injection with on-demand, per-file context.
- **In-kernel service-knowledge binding (3c502ee5 · xtrm-6z6.4).** `service_knowledge` is bound inside the kernel, so it can be called directly from kernel code.
- **Audit seam (650f8bd4 · xtrm-h7uwi.3).** Kernel mutation events are surfaced to the host, making kernel state changes observable for audit rather than opaque.
- **QoL: stdlib prelude and output truncation (8aa5b175 · xtrm-h7uwi.2).** Common stdlib modules are pre-loaded and long outputs are truncated with a shape hint instead of flooding the transcript.

## Claude channel wake

`xt claude` sessions no longer need to be polled to be driven.

- **Wake sessions through the Specialists channel (PR #650 · e3c09927 · XTRM-249).** A Claude session can be woken over the channel.
- **`--channels` on the direct launch path (PR #653 · d5cd4a68 · CORE-2283) and on attach resume (PR #654 · 2197709d · CORE-2284).** Both the direct launch and the attach/resume path now pass `--channels`, closing the gap where a resumed session lost channel reachability.
- **Surface channel-wake state in `xt doctor` (PR #655 · dc60e666 · CORE-2286, advisory).** Doctor reports channel-wake state so a silently unreachable session is diagnosable rather than invisible.

## Fixed during release preparation

Four defects blocked this release and are fixed before it ships. They are listed
here because each one would otherwise have shipped silently.

- **Substrate was resolved under the wrong npm scope (CORE-2324 · PR #669).** The CLI looked up `@xtrm/substrate`, a scope that 404s, and concluded from that 404 that the package was unpublished — hard-coding a refusal to install it. The real package is `@jaggerxtrm/substrate` (`bin sb -> dist/cli/sb-ux.js`). The premise was true for about seven hours: `f949b33f` landed 2026-09-11 20:40 UTC and `@jaggerxtrm/substrate@0.1.0` was published 2026-09-12 03:28 UTC. It then stayed stale for a month. `sb` is again a normally provisioned managed dependency, and `resolveSetupTs` accepts both the source-checkout layout (`integrations/setup.ts`) and the published layout (`dist/integrations/setup.js`).
- **The registry manifest was stale after the version bump (PR #668).** `gen-registry` stamps `package.json`'s version into every entry, so the release commit invalidated all 240. Regenerated; content hashes were untouched. **Process rule from here on: the version bump and `gen-registry` land together.**
- **Nothing validated registry content hashes (PR #667).** `check:registry-pack-parity` checked only the file *inventory*. `npm run check:registry-freshness` now runs in CI beside it, regenerating the manifest in memory and failing when it differs — naming the drifted paths. On its first genuine run it caught the stale manifest described above, which is the gate proving itself.
- **The release-contract assertions no longer matched the payload (CORE-2325 · PR #670).** They required three skills under a fresh project's `.xtrm/skills/default/`; `update-specialists` had moved to `optional/xtrm-maintenance` and `using-specialists-auto` no longer ships at all. The contract is now asserted against the installed package payload.

## Known limitation

**Fresh-machine `xt init` requires an authorized local substrate source.** Substrate-first init is deliberately fail-closed: enrollment provisions `sb` plus the Pi/Claude integrations from an authorized local checkout and aborts with exact remediation when no source resolves. A machine without that source — including a bare CI runner — cannot complete `xt init`, so it does not receive a project `.xtrm/skills/` tree.

This is a deliberate design decision, not a bug introduced here, and it is unchanged by this release. It is the reason the release-contract gate asserts the shipped payload rather than a fresh project's distribution: the latter cannot hold on a bare runner today. The product question — how a machine without a substrate source is expected to onboard — is tracked separately and is **not** resolved by 0.13.0.

**Consequence for operators:** provisioning remains `xt init --substrate-dir <checkout>` (or `XTRM_SUBSTRATE_DIR`) on any machine that does not already have an authorized substrate source.

## Upgrade notes

- **`.beads/` is no longer part of a checkout.** After updating, a repo's `.beads/` directory and its Git hooks are stale artifacts; remove them. Anyone with a `pre-push.bd-sync` hook wired into `.githooks/` should drop it — it now reports "no beads database in this checkout" and skips.
- **`xt memory` is gone.** Memory retrieval moves to the python-kernel file-scoped preflight and Substrate Journal. Scripts calling `xt memory` will fail; there is no compatibility alias.
- **`xt init` writes Substrate state.** It runs `sb init --json` and no longer performs Beads workspace/Dolt setup.
- **Project-scope hooks are no longer duplicated from global.** If you relied on a project-local copy of a globally-covered hook, it will no longer be written; the global install is authoritative.
- **Pair with Specialists 3.21.6.** The vendored payload is pinned by Git blob identity; floating refs are rejected by design.
- **Consumer refresh requires this published version.** `xt update --apply` resolves its payload from the installed CLI package, not the current working directory, so new skill content (including `using-xtrm`'s contract-quality checklist) only reaches a machine after installing a package containing it.
